Admin Overhaul · Angle 01 · Prototype Deck

Clinical outcomes first.
Everything else is a footnote.

An admin exists to answer one question: is this platform producing clinical outcomes? This design treats recovery, reliable improvement, and reliable recovery as the hero and relegates user counts, queues, and work volume to a subordinate operational strip. Suppression is not a failure state — it is a statement of rigour.

05Component breakdown

Reuses the existing bwell vocabulary heavily. Three new clinical-specific components are required; everything else composes from the inventory in §6 of the brief.

New — clinical-specific

Specific to the admin outcomes surface.

<OutcomeFigure />
The hero. Renders a single OutcomeResult: rate, n, suppressed reason. Handles the count-up animation + blur-on-suppressed treatment. Accepts an optional variant for layered rates.
<IAPTTriplet />
Recovery / reliable improvement / reliable recovery as a layered visual. Guarantees all three are shown together so an admin can never misread a single rate in isolation.
<SuppressedCell />
Primitive for "< 5 patients" / "n=12 · not yet reportable". Italic grey, tooltip explains reason (below_k vs below_min_n). Fundamental enough that it shows up in tables and time-series.
<TierCompareTable />
Three rows (self_help / cbt_guided / pwp_guided), three columns (recovery / rel.imp / rel.rec). Rows collapse to <SuppressedCell /> when below thresholds.
<RollupFreshnessBanner />
Renders rollupAsOf with traffic-light colouring (fresh ≤ 24h, stale > 25h, missing). Accepts privacyMode to show the dev-mode chip.
<OutcomeSeries />
Time-series chart that renders suppressed + zero-denominator buckets on-axis with distinct treatments. Wraps Sparkline/BarSparkline; adds tooltip with suppression reason.

Reused — from the inventory

From §6 of the brief; no modification.

Container / ContentContainer
Screen wrappers. Admin home uses ContentContainer with a three-tab header.
ThemedText
Every text node. title/subtitle/small across.
StatusChip / Chip
Care-tier pills, instrument chips ("PHQ-9", "GAD-7"), rollup status. Dev-mode banner uses the therapist purple tint.
BarSparkline / Sparkline
Hero trend line and per-programme spark rows.
Collapsible
Operational strip at the foot of the home screen.
EmptyState
Day-one "rollup pending" and zero-enrolment programme variants. Preserves content focus on the clinical surface.
ActionMenu
Verification confirmation (destructive variant). Tier picker is a required field in the confirm step, matching business rule §3.12.
SelectField / SearchPickerDialog
Dimension filters in the time-series explorer: programme, care tier, instrument.

06Rationale

Why this design serves the "does therapy work?" angle.

  • One question answered first. Recovery rate is the first visual element in the first fold at title weight. Counts, queues, and audit — the operational soup every admin dashboard leans on — are deliberately demoted. If the only thing an admin ever reads is the hero, they've read the right thing.
  • All three IAPT rates, always together. Showing recovery alone allows a kind regression to the mean to read as clinical success. Layering reliable improvement and reliable recovery underneath — with definitions visible — makes it structurally impossible for an admin to cite a single figure without its siblings.
  • Suppression is a first-class state. k-anonymity and min-N are the honest bones of clinical reporting. The design treats "< 5 patients" as aesthetically deliberate (italic grey, a micro-blur on reveal, a tooltip explaining why), not as a rendering failure. Every suppressed cell should feel like rigour, not absence.
  • Care-tier breakdown is the obvious drill-in. If the platform is working, the interesting second question is always "which tier is producing the outcome?" — self-help vs CBT-guided vs PWP-guided. The programme detail screen is one tap from the hero and answers that question directly.
  • Honest about freshness. rollupAsOf is surfaced on every outcome view. Day-one state (rollupAsOf: null) and stale-rollup state have distinct treatments. No admin should ever be looking at cached IAPT rates and not know it.
  • Non-clinical programmes are not faked. Sleep Health has no instrument — so it never shows a percentage. It gets an engagement indicator in a visually distinct treatment, so an admin can't accidentally conflate engagement with clinical outcomes.
BE assumption flag: the state gallery includes a "stale rollup" (> 25h) treatment that assumes the BE stamps rollupAsOf with the last successful completion — confirmed by §2.5. It also assumes the FE can observe rollup job status for the error banner via GET /api/admin/system/health.rollupLastRun — already specified. No new BE work required to implement this angle. If we wanted the "8 more paired assessments needed" micro-copy in the below-min-N state to be exact (rather than derived client-side from 20 − n), we'd want the BE to return shortfall on the OutcomeResult.
